# Documented preprocessing steps

This document records **what was done to the data, in what order, and why**. It is the
written companion to `src/preprocess.py`; every figure and number quoted here is
regenerated by running that script.

- **Dataset:** `data/customer_churn_raw.csv` — 1,800 synthetic customer records, 13 columns
- **Target:** `churn` (`Yes` / `No`)
- **Identifier:** `customer_id` — retained for traceability, excluded from model inputs
- **Seed:** `42` for every stochastic step

---

## The pipeline at a glance

```
raw CSV
  │
  ├─ 1. Load ..................... schema assertion, 1,800 × 13
  ├─ 2. Audit .................... 562 missing feature cells, 0 duplicates
  ├─ 3. Clean .................... trim, repair, deduplicate → 1,800 rows
  ├─ 4. Impute ................... median / mode + 4 indicators → 0 missing
  ├─ 5. Outlier audit ............ 3 flagged by IQR, 0 deleted
  ├─ 6. EDA ...................... 8 analysis figures
  ├─ 7. Encode ................... 6 categorical → 16 one-hot columns
  ├─ 8. Scale .................... 5 numeric → mean 0, std 1
  └─ 9. Select ................... mutual-information ranking + top 10
        │
        └─ model-ready matrix: 1,800 × 25, zero missing values
```

---

## Step 1 — Data loading

**What.** Read the CSV with Pandas, normalise column names, reset the index, and assert
that every expected column exists and that the target contains only valid labels.

**Why.** Three failure modes are cheap to catch here and expensive to catch later:

| Failure | Consequence if undetected | Guard |
|---|---|---|
| A column was renamed in the source system | Silently wrong model inputs | Explicit schema assertion raises |
| A literal `"unknown"` sits in a text column | Becomes a real category and is encoded as information | `na_values` lists it explicitly |
| The file is empty or truncated | Confusing downstream errors | Shape is printed and audited |

**Decision.** Declare missing-value tokens explicitly rather than relying on Pandas
defaults. Pandas recognises `""` and `"NA"`, but not `"unknown"`, `"N/A "` with a
trailing space, or `"-"`.

**Output.** In-memory `DataFrame`; the loaded shape is printed and recorded.

## Step 2 — Data-quality audit

**What.** Measure eight properties of the raw table without modifying it:

1. duplicate rows,
2. duplicate customer identifiers,
3. missing feature cells (count and percentage),
4. leading/trailing whitespace in text,
5. empty-string cells,
6. impossible negative values in numeric columns,
7. `senior_citizen` codes outside `{0, 1}`,
8. target values outside `{No, Yes}`.

**Why.** Auditing before changing anything is what makes the rest of the report
falsifiable. If you clean first, you can no longer report how much was missing or why.

**Findings on this dataset.**

| Check | Result |
|---|---|
| Duplicate rows | 0 |
| Duplicate customer IDs | 0 |
| Missing feature cells | **562** (2.84% of the 11 × 1,800 feature grid) |
| Columns with missing values | **10 of 11** (`senior_citizen` is complete) |
| Whitespace defects | 0 |
| Empty strings | 0 |
| Impossible negative values | 0 |
| Invalid `senior_citizen` codes | 0 |
| Invalid target values | 0 |

**Output.** `outputs/data_quality_checks.csv`.

> Reporting zero findings is still reporting. A quality table that lists only the
> defects it found gives a reviewer no way to know the other checks ran at all.

## Step 3 — Cleaning

**What and why, rule by rule.**

| Rule | Reason | Effect here |
|---|---|---|
| Trim whitespace in text columns | `" Month-to-month"` and `"Month-to-month"` would become two different categories after one-hot encoding | 0 cells trimmed |
| Treat empty strings as missing | An empty string is the absence of a value, not a level of a category | 0 cells |
| Convert negative charges, tenure, ticket counts to missing | A negative bill is impossible, not merely unusual; leaving it corrupts the mean, the scaler and any distance calculation | 0 cells |
| Convert `senior_citizen` values outside `{0,1}` to missing | A binary flag must be binary; other codes are data-entry faults | 0 cells |
| Remove rows with a missing or invalid target | **Labels cannot be imputed.** A guessed label teaches the model something false | 0 rows |
| Remove exact duplicate rows | A duplicated record is double-weighted during training | 0 rows |
| Keep the first occurrence of each `customer_id` | Duplicate identifiers imply conflicting attributes for one entity; they must be investigated rather than averaged | 0 rows |

**Why impossible values become missing rather than being clamped.** Clamping invents a
value that was never recorded. Setting to missing hands the problem to the imputer,
which uses a defensible estimate, and the missing indicator records that something was
repaired.

**Outcome.** 1,800 rows in, 1,800 rows out. The dataset was clean enough that no rows
had to be sacrificed, which preserves the full sample for later weeks.

**Output.** `outputs/cleaned_customer_churn.csv` (written later, after imputation),
plus the cleaning log inside `preprocessing_summary.json`.

## Step 4 — Handling missing values

### 4.1 Audit

| Feature | Kind | Missing | % | Strategy | Fill value |
|---|---|---|---|---|---|
| `support_tickets` | numeric | 89 | 4.94 | median + indicator | 1.00 |
| `monthly_charges` | numeric | 78 | 4.33 | median + indicator | 64.34 |
| `tenure_months` | numeric | 77 | 4.28 | median + indicator | 37.00 |
| `total_charges` | numeric | 74 | 4.11 | median + indicator | 2,020.29 |
| `payment_method` | categorical | 52 | 2.89 | most frequent | Bank transfer |
| `contract` | categorical | 47 | 2.61 | most frequent | Month-to-month |
| `internet_service` | categorical | 42 | 2.33 | most frequent | Fiber optic |
| `paperless_billing` | categorical | 36 | 2.00 | most frequent | Yes |
| `dependents` | categorical | 34 | 1.89 | most frequent | No |
| `partner` | categorical | 33 | 1.83 | most frequent | Yes |
| `senior_citizen` | numeric | 0 | 0.00 | none needed | — |

**Total filled: 562 cells.** Output: `outputs/missing_value_audit.csv`.

### 4.2 Why the mechanism matters

The right method depends on *why* data is missing, and that cannot be proven from the
data alone:

| Mechanism | Meaning | Consequence |
|---|---|---|
| **MCAR** | Missingness is unrelated to any variable | Deletion is unbiased but wasteful; any sensible imputation works |
| **MAR** | Missingness depends on observed variables | Conditional or model-based imputation is defensible |
| **MNAR** | Missingness depends on the missing value itself | No imputation is unbiased; add an indicator and state the assumption |

Here the blanks were introduced by a random masking step, which is closest to MCAR. The
chosen strategy is nevertheless safe under MAR, and the indicators cover the possibility
that missingness itself carries signal.

### 4.3 Why median for numbers

Every numeric column is skewed or contains extreme values. The mean is pulled toward
those extremes; the median is not. Filling a skewed column with its mean places the
synthetic value somewhere the typical customer never is.

### 4.4 Why mode for categories

There is no arithmetic on unordered categories. The mode is the only summary guaranteed
to be a real, valid level of the variable.

### 4.5 Why missing indicators

`SimpleImputer(add_indicator=True)` adds a 0/1 column for each numeric feature that had
gaps. This preserves the fact that a value was absent, in case absence is informative —
at the cost of four extra columns in the final matrix.

### 4.6 Why not delete rows

Dropping every row with at least one missing cell would leave only **1,303 of 1,800
rows** — losing 27.6% of the data and biasing what remains toward customers with complete
records. That trade is not worth it when every column is at most 5% missing.

### 4.7 The measured cost

Imputation is not free: filling several per cent of a column with one repeated value
creates a **spike** at that value and **shrinks the variance**. This is measured, not
assumed — the before/after means and standard deviations are exported to
`outputs/scaling_summary.csv`, and the spike is visible in Figure 4 of the report and in
Section 5.4 of the notebook.

## Step 5 — Outlier audit

**Method.** The 1.5 × IQR rule: flag any value below `Q1 − 1.5·IQR` or above
`Q3 + 1.5·IQR`.

**Important exception.** Binary 0/1 flags are excluded from the screen. In a column that
is mostly zero, every single `1` falls outside the fences — flagging 319 senior citizens
as "outliers" would be a category error, not a finding.

| Feature | Q1 | Q3 | IQR | Upper fence | Flagged | Action |
|---|---|---|---|---|---|---|
| `tenure_months` | 23.00 | 52.00 | 29.00 | 95.50 | 0 | No outliers |
| `monthly_charges` | 47.78 | 78.06 | 30.28 | 123.48 | 0 | No outliers |
| `total_charges` | 1,082.97 | 3,205.17 | 2,122.20 | 6,388.46 | 2 | Retained |
| `support_tickets` | 0.00 | 2.00 | 2.00 | 5.00 | 1 | Retained |
| `senior_citizen` | — | — | — | — | — | Not assessed (binary flag) |

**Decision: retain every flagged value.** Three reasons:

1. The values are **plausible** — a long-tenure customer with a large cumulative bill is
   a real, commercially important case, not an entry error.
2. Deleting them would **discard exactly the customers a churn study cares about** and
   bias every downstream statistic.
3. The pipeline already protects scale-sensitive algorithms: standardisation (Step 8)
   removes unit effects, and later weeks use tree models that are robust to extremes.

**Output.** `outputs/outlier_audit.csv`.

- **Target:** 73.3% No, 26.7% Yes. A constant-negative model scores 73%, so accuracy is

- **Missingness:** evenly spread at 1.8–4.9% across ten columns — no column is so

- **Numeric shape:** `monthly_charges` and `total_charges` are right-skewed;

- **Collinearity:** `tenure_months` ↔ `total_charges` = 0.75 and `monthly_charges` ↔

> Every statement above describes this synthetic sample. None of it is causal, and none
> of it generalises to real customers.

## Step 7 — Encoding categorical variables

**Method.** `OneHotEncoder(handle_unknown="ignore", sparse_output=False)`.

| Feature | Levels | Encoded columns |
|---|---|---|
| `contract` | 3 | 3 |
| `internet_service` | 3 | 3 |
| `payment_method` | 4 | 4 |
| `paperless_billing` | 2 | 2 |
| `partner` | 2 | 2 |
| `dependents` | 2 | 2 |
| **Total** | **16 levels** | **16 columns** |

**Why one-hot rather than ordinal or label encoding.** The levels have no meaningful
order. Coding `Month-to-month = 0, One year = 1, Two year = 2` would impose a numeric
distance on the model that does not exist in reality, and a linear model would be forced
to treat "Two year" as twice "One year". One-hot makes each level its own independent
yes/no column.

**Why scikit-learn's encoder rather than `pd.get_dummies`.**

1. It **stores** the category list learned during fitting. `get_dummies` derives columns
   from whatever data it is handed, so a level present in training but absent at
   prediction time produces a different column set and the model fails.
2. `handle_unknown="ignore"` encodes an unseen level as all zeros instead of raising. A
   new contract type may appear after deployment; the model should degrade, not crash.
3. It can be serialised together with the model as a single object.

**The dummy-variable trap.** Keeping every one-hot column makes the block perfectly
collinear: each row's indicators sum to 1 within a feature, so any column is a linear
combination of the others. Regularised models handle this without difficulty, but the
interpretive consequence must be stated — **individual one-hot coefficients are not
independent effects**. Dropping a reference level (`drop="first"`) would restore
interpretability at the cost of asymmetric treatment of levels. This project keeps all
levels and documents the trade-off.

**Output.** `outputs/encoding_summary.csv`; encoded columns appear in
`outputs/preprocessed_customer_churn.csv`.

## Step 8 — Normalisation and scaling

**Method.** `StandardScaler` — `x' = (x − mean) / std`.

**Why scaling is necessary.** `tenure_months` ranges over roughly 1–71 while
`total_charges` reaches several thousand. Any algorithm that computes distances (KNN,
K-Means, SVM) or applies a regularisation penalty compares features by magnitude, so an
unscaled `total_charges` would dominate purely because of its units.

**Which scaler, and why.**

| Method | Formula | Output | When it is right |
|---|---|---|---|
| **Standardisation (chosen)** | `(x − mean) / std` | mean 0, std 1 | Default for skewed or unbounded numerics; preserves outlier structure |
| Min–max normalisation | `(x − min) / (max − min)` | exactly `[0, 1]` | Bounded inputs, e.g. pixel values or neural-network inputs |
| Robust scaling | `(x − median) / IQR` | centred on the median | Heavy outliers that must not influence the scale |

Standardisation was chosen because the numeric features are skewed with long tails.
Min–max would compress the bulk of the distribution into a narrow band whenever a single
large outlier is present, which is exactly the situation in `total_charges`.

**Verification.** The transformation is checked rather than assumed:

| Feature | Mean before | Std before | Mean after | Std after |
|---|---|---|---|---|
| `tenure_months` | 37.193 | 17.434 | −0.0000 | 1.0003 |
| `monthly_charges` | 60.727 | 21.816 | −0.0000 | 1.0003 |
| `total_charges` | 2,227.577 | 1,372.352 | 0.0000 | 1.0003 |
| `support_tickets` | 1.002 | 1.049 | 0.0000 | 1.0003 |
| `senior_citizen` | 0.177 | 0.382 | 0.0000 | 1.0003 |

**What scaling does not do.** It is monotonic, so it does not change the rank order of
values within a column, and it does not make a skewed distribution symmetric — Figure 8
shows the shape is preserved and only the axis is rescaled.

**Leakage warning.** The scaler must be fitted on the **training split only**. Using the
mean and standard deviation of the full dataset before splitting lets test information
influence the training transformation. The effect on a large sample is small — which is
exactly why the mistake survives review, because it is invisible in the output and shows
up only as a slightly optimistic score. In this project the scaler lives inside a
`ColumnTransformer`, so cross-validation refits it on every fold automatically.

**Output.** `outputs/scaling_summary.csv`.

## Step 9 — Feature selection

**Method.** Mutual information (`mutual_info_classif`), with one-hot columns, binary flags
and missing indicators declared **discrete** and `n_neighbors=5`.

**Why mutual information rather than correlation.** Correlation measures only *linear*
association and requires a numeric target. Mutual information captures non-linear
dependence and works with a categorical target. A correlation of zero proves nothing;
a mutual-information score of zero is at least evidence that no *detectable* dependence
exists in this sample.

**Why `n_neighbors=5` rather than the default 3.** The k-NN estimator is noisy at this
sample size. With 3 neighbours, weak but genuine signals such as `tenure_months`
collapse to exactly 0.0 — an artefact of the estimator, not a fact about the data.

| Rank | Feature | Mutual information |
|---|---|---|
| 1 | `monthly_charges` | 0.0592 |
| 2 | `internet_service_Fiber optic` | 0.0422 |
| 3 | `contract_Month-to-month` | 0.0399 |
| 4 | `contract_Two year` | 0.0304 |
| 5 | `internet_service_No` | 0.0212 |
| 6 | `support_tickets` | 0.0140 |
| 7 | `internet_service_DSL` | 0.0125 |
| 8 | `total_charges` | 0.0092 |
| 9 | `contract_One year` | 0.0064 |
| 10 | `senior_citizen` | 0.0009 |
| 11 | `payment_method_Electronic check` | 0.0007 |
| 12 | `dependents_No` | 0.0006 |

Two independent views agree: mutual information ranks `monthly_charges`, the Fiber-optic
indicator and the contract indicators at the top, and the descriptive group rates in
Step 6 show the same three variables separating the target most strongly. Agreement
between a model-free score and a simple group comparison is a useful sanity check that
encoding did not corrupt the category structure.

### Two honest caveats

1. **Scores are marginal.** Mutual information scores each feature on its own. A
   weak-but-real signal can score near zero, and two individually uninformative features
   can still be jointly valuable. The ranking orders usefulness; it does not prove
   uselessness.
2. **This ranking used the full sample.** That is acceptable for an explanatory report
   artefact but **not for modelling**. Any feature selection used to train a model must be
   re-fitted inside the training folds, exactly like imputation and scaling. The
   distinction is recorded in `preprocessing_summary.json` and repeated in the report.

**Output.** `outputs/feature_selection.csv` (full ranking) and
`outputs/selected_feature_dataset.csv` (top 10 + id + target).

## Limitations

| Limitation | Why it matters | What real use would require |
|---|---|---|
| Synthetic data | Patterns are properties of the generator | Validation on representative, permitted production data |
| Random missingness | Real missingness is usually systematic, so median imputation would be biased | Analysis of the missingness mechanism; model-based imputation |
| Median/mode imputation understates variance | The fill value creates a spike and narrows the spread | Comparison against multiple imputation |
| Feature ranking uses the full sample | Acceptable for explanation, not for model selection | Re-fit selection inside cross-validation folds |
| No fairness analysis | Imputation rates can differ systematically by group | Audit missingness and error rates by subgroup |
| Association is not causation | Churn-rate differences are descriptive | A controlled study or causal-inference methods |
